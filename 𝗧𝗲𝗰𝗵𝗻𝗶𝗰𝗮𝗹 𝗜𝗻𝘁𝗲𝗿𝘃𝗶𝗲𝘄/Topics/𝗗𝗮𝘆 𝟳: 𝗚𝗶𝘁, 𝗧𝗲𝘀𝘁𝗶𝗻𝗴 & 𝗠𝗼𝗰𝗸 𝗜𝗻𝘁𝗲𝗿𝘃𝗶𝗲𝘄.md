## 1. Git Branching

### Core idea

Git branching allows multiple developers to work on different features without modifying the main branch directly.

```text
                    feature/auth
                   /
main ─────────────●────────────●──────
                 /
        feature/payment
```

Typical workflow:

```text
main
 │
 ├── feature/login
 │      │
 │      ├── commit
 │      ├── commit
 │      └── PR
 │
 └── feature/payment
        │
        ├── commit
        └── PR
```

### Interview answer

> I normally create a feature branch from the latest main/develop branch, make isolated commits, push the branch and create a pull request. This keeps production code stable and allows code review before merging.

### Commands

```bash
git checkout main
git pull origin main

git checkout -b feature/login

git add .
git commit -m "Add login API"

git push -u origin feature/login
```

# 2. Merge vs Rebase ⭐

This is one of the most commonly asked Git questions.

### Merge

```text
A──B──C────M──
     \    /
      D──E
```

Merge combines histories and creates a merge commit.

```bash
git checkout main
git merge feature/login
```

### Rebase

```text
A──B──C──D──E
          ↑
       feature
```

Rebase moves your commits on top of the latest base.

```bash
git checkout feature/login
git rebase main
```

### Main difference

| Merge                            | Rebase                            |
| -------------------------------- | --------------------------------- |
| Preserves history                | Rewrites commit history           |
| Creates merge commit             | Usually linear history            |
| Safer for shared branches        | Good for private feature branches |
| Doesn't rewrite existing commits | Changes commit hashes             |

### Golden interview answer

> I prefer rebase for my local/private feature branch when I want a clean linear history. I avoid rebasing commits that other developers are already working on because rebase rewrites history. For shared branches, merge is generally safer.

### Critical question

**Can you rebase a public branch?**

> Technically yes, but I generally avoid it because it rewrites commit history and can cause problems for other developers who already based their work on those commits.

# 3. Conflict Resolution

Imagine:

```text
main:
A ── B ── C

feature:
A ── B ── D
```

Both modified the same code.

Git:

```text
<<<<<<< HEAD
main version
=======
feature version
>>>>>>> feature/login
```

### Resolution process

```bash
git pull
```

If conflict occurs:

```bash
git status
```

Open the conflicting files and decide which implementation should remain.

Then:

```bash
git add .
git commit
```

For rebase:

```bash
git add .
git rebase --continue
```

To cancel:

```bash
git rebase --abort
```

### Interview answer

> I don't blindly choose ours or theirs. First I understand why both changes were made, determine the intended behavior, resolve the code accordingly, run tests, and then complete the merge or rebase.

That sounds much stronger than:

> "I remove the conflict markers."

# 4. Revert vs Reset ⭐

Very important.

### Reset

Moves the branch pointer.

```text
Before:

A ── B ── C ── D
              ↑
             HEAD

git reset --hard B

A ── B
```

Commands:

```bash
git reset --soft HEAD~1
git reset --mixed HEAD~1
git reset --hard HEAD~1
```

### Revert

Creates a new commit that reverses an earlier commit.

```text
A ── B ── C ── D ── E
              ↑
          revert C
```

### Interview answer

> I use `git revert` when the commit has already been pushed/shared because it preserves history. I use `git reset` mainly for local commits that haven't been shared.

### Remember

```text
Shared history  → revert
Private history → reset
```

# 6. Unit Testing ⭐

A unit test tests a small isolated piece of logic.

For example:

```python
def calculate_discount(price, discount):
    return price - (price * discount / 100)
```

Test:

```python
def test_calculate_discount():
    assert calculate_discount(1000, 10) == 900
```

### What should you test?

```text
                 Function
                    │
       ┌────────────┼────────────┐
       ▼            ▼            ▼
    Normal       Invalid       Edge
     Case         Input         Case
```

Example:

```text
price = 1000
discount = 10
→ 900

price = 1000
discount = 0
→ 1000

price = 1000
discount = 100
→ 0

price = 1000
discount = -10
→ validation/error
```

### For your FastAPI projects

You should be comfortable with:

```text
pytest
   +
FastAPI TestClient
   +
mocking external services
```

Example:

```python
def test_create_company(client):
    response = client.post(
        "/companies",
        json={"name": "Infosys"}
    )

    assert response.status_code == 201
```

# 8. Mocking

This is especially important for **your YouTube/Grok/RAG work**.

Suppose your service calls:

```text
YouTube API
     ↓
YouTube Connector
     ↓
Your Service
```

Don't call the real YouTube API in every unit test.

Instead:

```text
Test
 │
 ▼
Mock YouTube Client
 │
 ▼
YouTube Connector
 │
 ▼
Your Service
```

### Why?

> Unit tests should be deterministic, fast and independent of external services.

Example with `unittest.mock`:

```python
@patch("app.clients.youtube_client.YouTubeClient.search_videos")
def test_search(mock_search):
    mock_search.return_value = [
        {"id": "abc123"}
    ]

    result = service.search("Infosys")

    assert result[0]["id"] == "abc123"
```

 ▼

 │
 ▼

### Don't say:

> "I put print statements."

> I first reproduce the issue, identify the failing layer, inspect logs and request/response data, isolate the root cause, implement the smallest appropriate fix, and then add a regression test.
